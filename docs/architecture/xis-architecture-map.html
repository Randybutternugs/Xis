How the Tull website is built and what talks to what

Xis is one Flask application (the xissite/ package) deployed to Google App Engine as tullhydro.com, plus a second, separate Flask app (admin_panel/) that runs only on the LAN and proxies to the first one's admin API. Everything below was read from the code, not the docs, and where the two disagree the code wins and the disagreement is listed at the end.

// 01 system context

Five parties, one app in the middle

The website is the only thing on the public internet. Stripe and Postmark are called from it; TullOps and the admin panel call into it from the LAN using one shared Bearer key. Nothing on the internet can reach the LAN, so the LAN always initiates.

// 02 request path

What a request passes through

App Engine answers static files itself. Everything else reaches gunicorn, then the app factory's middleware, then one of four blueprints. The factory in xissite/__init__.py also decides, at import time, whether it is running locally or in the cloud and which database URI to use.

Startup sequence inside create_app()

  • Environment detection. If GAE_ENV, GAE_APPLICATION or GOOGLE_CLOUD_PROJECT is set it is "cloud"; otherwise it loads vars.env with python-dotenv.
  • Database URI. DATABASE_URL or CLOUD_SQL_URI wins if present. Otherwise SQLite at /tmp/tullhydro.db in the cloud or ./tullhydro.db locally.
  • Session hardening. 8 hour sessions, 7 day remember-me, HttpOnly + SameSite=Lax, Secure cookies only when not in development.
  • Extensions and blueprints. CSRFProtect (with WTF_CSRF_CHECK_DEFAULT=False, so CSRF is checked only where a form validates or a route asks), SQLAlchemy, then the four blueprints, then a to_eastern Jinja filter.
  • create_database(). db.create_all(), then 16 idempotent "add column if missing" migrations, then deletes legacy users whose email is a hash artifact, then creates the bootstrap admin from ADMIN_BOOTSTRAP_* if the user table is empty.
  • Flask-Login. Login view is auth.login; the user loader is a primary-key lookup on User.

Admin panel (ARCS only, port 5002)

RouteWhat it does
/site-admin, /users, /logins, /customers, /purchases, /feedback, /visitors, /securityEight template pages generated from one PAGES tuple, which also drives the nav so they cannot drift. No authentication; the only protection is that it binds 127.0.0.1 unless ADMIN_PANEL_HOST says otherwise.
/api/site-admin/export/<table>Forwards upstream and adds a Content-Disposition: attachment header so the browser downloads the CSV.
/api/site-admin/<path>GET/POST/PUT/DELETE catch-all. Forwards to TULLSITE_API_URL/api/admin/<path> with the Bearer header, 10 s timeout, and maps timeout to 504 and connection failure to 502. The key never reaches the browser. POST, PUT and DELETE are refused with 403 unless they carry X-Requested-With and, if present, an Origin equal to the panel's own. The base template adds that header to every same-origin fetch, so a page in another tab cannot drive the passthrough.

// 06 data model

Nine tables, one real relationship

Only customer to purchase is a declared foreign key. The security and analytics tables relate to each other by IP address value, which is why the dashboard resolves and caches GeoIP per IP rather than per row.

// 07 security model

Who can do what, and what stops the rest

LayerMechanismWhere
TransportApp Engine forces HTTPS on every handler; Secure cookie flags on in production.app.yaml · __init__.py
RolesTwo roles. admin sees everything. employee sees only /ops. Investor role was removed in the March 2026 overhaul and a test guards against its return.auth.py · tests/test_investor_removal.py
SuspensionApplies to admins and employees alike. The session loader drops any account that is not active, so a suspended or deleted user loses access on their next request, not at their next login. The bootstrap admin can never be suspended, deleted or demoted, and a browser session cannot disable its own account.auth.py · __init__.py · admin_api.py
PasswordsWerkzeug scrypt. Minimum 10 characters enforced by the API, no complexity rules. A dummy hash is computed for unknown usernames to blunt timing enumeration.admin_api.py · auth.py

Machine accessOne static Bearer key for the whole admin API, compared in constant time. No per-caller keys, no rotation mechanism, no rate limit on the key path.admin_api.py
InputsEvery numeric query or body parameter goes through one bounded parser. Non-numeric values answer a JSON 400; days is capped at 365. Export cells that could be spreadsheet formulas are neutralised.admin_api.py
CSRFGlobal check is off. Enforced where a WTForm validates (contact, /viewdb search) and by the X-CSRFToken header on session-authenticated API mutations. Webhook and checkout routes are exempt on purpose.views.py · admin_api.py · sales.py
SpamSix-layer guard on the contact form, described in flow B.spam_guard.py
AuditEleven admin actions write admin_audit_log with the caller IP.admin_api.py
Admin panelNo login. Its protection is network position plus a same-origin guard: mutating requests need a custom header and a matching Origin, which a page in another tab cannot supply. Binds loopback by default; the README forbids port-forwarding or a Tailscale funnel. Refuses to start without the key so a misconfiguration fails loudly instead of silently 401ing. Every value it renders is escaped for both text and attribute contexts, and a test fails on any raw interpolation of attacker-controlled fields.admin_panel/api.py · config.py · templates

// 09 observations

Where the code, the docs and the intent disagree

Found while mapping and auditing on 2026-09-20. Green items were fixed and deployed that day. The rest are still open, ordered by how much they would surprise someone operating the site.

  • fixedLocked accounts and expiring bans crashed the login route; feedback resolve, stats and reply crashed too. SQLite returns datetimes without a zone; comparing them to an aware now() raised. Normalised through timeutil.as_utc(), with tests that reload the rows the way a second request does.
  • fixedScript injection through the local panel's Logins page. The User-Agent of every public login attempt was rendered unescaped, so one crafted failed login ran script in the panel, which holds the API key. Escaped, and a source-level test now fails on any raw interpolation of attacker fields in any panel template.
  • fixedThe local panel forwarded requests from any website open in the same browser. Body-less POSTs need no CORS preflight. Mutations now require a same-origin marker header and a matching Origin.
  • fixedMost panel pages showed blanks or lied about success. They read field names the API never sent and sent filters it never read. Every page is rewritten against the real shapes, dead features (revenue, customer tags, Investor role) are removed, and a contract test pins template field names and query parameters to the API.
  • fixedA deploy would have uploaded the local secrets file and SQLite database. Both are now in .gcloudignore, with a test.
  • fixedSuspend did nothing for admins and never ended a live session; PUT could soft-delete the protected bootstrap admin; an admin could disable their own account. Suspension applies to everyone, the session loader drops inactive accounts, and the bootstrap admin and your own session are refused.
  • fixedCSV formula injection, 500s on non-numeric parameters, replies reporting success when the email failed, GeoIP failures silently dropped, and a non-constant-time key compare. All in admin_api.py, each with a test.
  • fixedSite dashboard: quotes not escaped in tooltips, success toasts on failed actions, usernames never shown, a section stuck on "Loading". Also the devices breakdown endpoint, which had answered 500 everywhere because its user-agents dependency was never listed.
  • eventGoogle Cloud billing had lapsed and the site returned 503. Billing was restored on 2026-09-20, the site came back on the April build, the fixes above were deployed the same day, and 76 stale App Engine versions were deleted. Each restart or deploy still resets the database (next item).
  • highEvery deploy or instance restart erases users, customers, purchases, feedback and all security history. SQLite lives in /tmp. The bootstrap admin is recreated from env vars, but the accounts seeded by seed_users.py (for example the employee account) are gone until TullOps recreates them. This happened twice on 2026-09-20 alone: once when billing came back, once on deploy. Cloud SQL is the intended fix and is one env var away in code, but a real migration in practice.
  • highThe purchase pipeline is built but not reachable. /sell is a "coming soon" page whose only call to action is /contact. Nothing posts to /create-checkout-session, so Stripe, the webhook, customer and purchase tables, and the order email are all live code with no traffic. The dashboard's Orders and Customers panels will stay empty until a buy button exists.
  • mediumTullOps content push does not exist yet. The design says TullOps pushes tasks, checklists and notifications to employees through the admin API. There is no endpoint for that; /ops renders placeholder content hardcoded in the template (commit d463c10). The API today is read-mostly plus user management.
  • mediumThree admin front ends for one dataset. The in-site /admin JS dashboard, the legacy /viewdb pages, and the local admin panel all show the same data. The panel is now the one that is wired correctly and tested against the API. The Postmark admin-notification email still deep-links to the legacy feedback page, not to /admin.
  • mediummanage_db.py targets a schema that no longer exists. It queries table purchase__info with columns first_name, last_name, paid; the models use purchase_info, name, pay_status. Its users command also claims credentials live in env vars, which stopped being true in March. The status, purchases and export commands will error or skip on a current database. MANAGEMENT_GUIDE.md's schema section has the same stale shape.
  • mediumOne startup migration checks the wrong table name. add_product_name_column inspects purchase__info (double underscore), finds nothing, tries to ALTER a table that does not exist, and is swallowed by the bare except on every boot. Harmless today because new databases get the column from the model, but it prints a misleading "Running" line each start.
  • lowLogin POST does not check its CSRF token. The route reads request.form directly instead of calling form.validate_on_submit(), and the global CSRF check is off. Impact is limited to login CSRF, but the token in the template is decorative. Not changed today.
  • lowTwo different ideas of the client IP. Login trusts remote_addr (correct behind App Engine). The contact form trusts the first X-Forwarded-For value, which a client can set, so the contact rate limit can be sidestepped by spoofing the header.
  • lowHardcoded order total. fulfill_order emails "$200" regardless of what Stripe charged; the price lives only in the Stripe Price object.
  • lowDocs drift. README lists a dataviz.html that does not exist, omits /admin, /ops and the whole /api/admin surface, and app.yaml comments still mention Mailgun although all email moved to Postmark.
